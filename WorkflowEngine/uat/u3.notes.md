# u3.js notes (Faisal: procurement, warehouse, supply chain, manufacturing)

## Doc deviations (document says / API does / expected figure instead)
- U3-01 "all items visible with zero stock in each location": stock rows are created on the first movement, so there are no zero rows; the step asserts qty 0 or absent. Stock is kept per BRANCH code (JED/DMM/RYD), not per warehouse or bin: JED-MAIN = branch JED, DMM-STORE = DMM, RYD-HOSP = RYD. wh/location records are descriptive only.
- U3-04/05 "Over 5,000 enters the Purchase over 5,000 workflow, under 5,000 goes straight to Approved": there is no such workflow. Every PO is created Draft; approval is the separate action pos/{id}/approve by a user with proc.po.approve who is not the creator (Faisal lacks proc.po.selfApprove). All three POs (47,380.00 / 8,625.00 / 1,230.50) stay Draft until Noura approves them (u2 must do this on day 1, before u3 day 2). Faisal then does send (optional) and receive.
- U3-03 evaluation: weighted score 60% price / 40% delivery is calculated by the script (price = cheapest/own, delivery = fastest/own) and stored in the evaluation record; the API has no ranking function. Gulf 100.00, Red Sea about 79.37. RFQ quotes hold totals (16,000 / 16,800).
- U3-07 MRP: the Planning screen computes MRP in the browser; the script computes the same need (1,500 m / 2,000 / 100) against GET mfg/stock. To make the document's cost figures reachable the script sets work centre WC-SEW at 120/h, mfg defaults overheadPct 25, BOM routing 3.48 min (standard 41.30 + 6.96 + 1.74 = 50.00).
- U3-08 "report 100 made, then reject 2": the work order is completed with qty 98 good + scrap 2 (materials are issued for 100, finished stock 98, scrapQty 2). The quality inspection (defects 2, status Passed) is a separate record and does not change stock.
- U3-09 variance: the system compares actual 5,000.00 with the standard of all 100 produced (5,000.00) so work order `variance` = 0.00. The document's 100.00 unfavourable is (51.02 - 50.00) x 98 good packs = 99.96; the script asserts unitCost 51.02, material 4,130, labour 696 + overhead 174 = 870, actual 5,000, and that the per-pack figure is about 100.
- U3-11 picks: confirming a pick list lowers JED stock, but the sales orders (workflow documents) are not linked, so they never show Picked. Listed as manual U3-11b.
- U3-12 shipment "timeline shows each status change with time": a shipment record only keeps its current status plus createdAt/updatedAt; there is no status history. The script checks Planned -> InTransit -> Delivered and the tracking number. Forecast "suggests reorder": no API; the script checks the item reorder level (1,000) against stock after month 1 (1,460 - 1,000 = 460).
- U3-13 "Gulf order Closed": the real status is Received (there is no Closed). THERM stock 90 as in the document.
- U3-14 "Submit; approve the adjustment": a count is Draft then counts/{id}/post (wh.count.approve, which Faisal has). Variance -8 / -64.00 and stock 1,452 as in the document. NO GL journal is created by the count (the "Inventory adjustment 64.00 in the GL" does not happen via API), so Noura will not find it; expect none.
- U3-15 "Inventory document": the ERP · Stock Transfer workflow instance is started by Faisal (history shows him). It does not move stock, so the script also does the real movement with api/pos/transfers (+receive). JED SM 1,252, RYD 200.
- U3-16 decline "with the note Port inspection": the RSVP API takes only yes/no/maybe, there is no note field; the script declines with `no` and checks that Sara sees it. "Propose Tuesday 11:00" = POST calendar/freebusy for next Tuesday 08:00-09:00 UTC (11:00 Riyadh); the script lists who is free. Faisal must be in the attendee list of Sara's meeting (u5), username ctx.users.faisal.
- U3-17: a PO is not a workflow instance. There is no approver field and no approval comment ("Within Q4 budget" is stored in the PO notes of the Eastern/Packaging orders only for those two). The step checks requester Faisal, Approved (or later) status and createdAt <= updatedAt; it also starts a Purchase Requisition (Procure-to-Pay) workflow document as requester to cover "Workflow (as requester)". That document stays open at Manager Approval.

## Effect on Noura's bill timing (PO can be invoiced only when status Received)
- Gulf order: partly received on day 2, balance on day 4 (U3-13). It can be invoiced only AFTER U3-13 on day 4 and then as ONE draft bill for the whole order: 41,200 + VAT 6,180 = 47,380.00 (not an earlier bill plus the 632.50 extra bill). So Noura's payables on day 5 differ from the document: no separate 632.50 bill; the Gulf draft bill is 47,380.00 and appears only from day 4. Because u3 runs before u2 on each day, Noura on day 4 sees the Gulf order Received.
- Eastern (8,625.00) and Riyadh Packaging (1,230.50) are fully received on day 2, so Noura can invoice them from day 2 (after approval on day 1).
- Invoice is a DRAFT AP invoice (BILL-yyyy-nnnn) based on received quantity x price.
